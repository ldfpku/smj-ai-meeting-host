# 模型选型

调研与实测日期：2026-09-27，2026-09-28 补充了模拟会议的结果（2.7 节）。本文记录当前用了哪些模型、为什么、实测表现如何，
以及将来做本地化部署时可选的开源模型。

**怎么读本文的数据**

| 标注 | 含义 |
|---|---|
| 实测 | 在本项目里实际调用得到的结果，可复现 |
| 官方文档 | 来自 Google / TypeSafe / Hugging Face 的官方页面。调研时经过工具摘要，数字在对外引用前请到原页面复核 |
| 未验证 | 只有第三方说法，或模型卡自述、没有独立评测 |

## 1. 当前使用的模型

| 用途 | 模型 | 为什么选它 |
|---|---|---|
| 实时主持 | `gemini-3.8-live` | 2026-09-15 正式发布。讨论切题时能保持静默，只在需要时开口；此前的 3.1 每一轮发言都会回应 |
| 实时主持（备选） | `gemini-3.8-live-extended-thinking` | 开口前思考更充分，响应更慢 |
| 实时主持（备选） | `gemini-3.1-flash-live-preview` | 上一代预览模型，保留作回退 |
| 跑题判断 | TypeSafe Jev（`jev-latest`，当前指向 `jev-1.13.0`） | 不生成文字，只回答结构化问题并给出概率，因此偏题判断可量化、阈值可调 |
| 跑题判断用的识别 | `gemini-3.5-transcribe-live` | 边说边给出识别结果，发言人还没停顿就能判断。只用于跑题判断，见 2.7 |
| 打断语音 | `gemini-3.8-flash-tts` | 打断用语固定，每个议题开始时预先合成，判定跑题后直接播放 |
| 纪要整理 | 公司 AI 网关上的 `glm-5.3-flash`（Cloudflare Workers AI） | 满足数据私有化的要求。实测见 improvement-plan.md 3.8 |
| 纪要整理（备选） | `gemini-3.8-flash` | 网关失败时使用。上下文 100 万 token；支持按 JSON 结构输出 |
| 音色试听 | `gemini-3.8-flash-tts` | 2026-09-22 正式发布。更便宜的备选是 `gemini-3.8-flash-lite-tts` |

已移除：`gemini-2.5-flash-native-audio-preview-12-2025`。Google 自 2026-09-18 起限制 2.5 系列的访问。
存量预设或分享链接里若还指向它，会自动落到 `gemini-3.8-live`。

项目的 API 密钥已确认能访问上表所有 Gemini 模型（实测：调用模型列表接口）。

### 1.1 Gemini 3.8 Live 与之前版本的差异

这些差异决定了 `agent/model_caps.py` 里的取值。

| 项目 | 3.8 Live 的行为 | 本项目的处理 | 依据 |
|---|---|---|---|
| 输出形式 | 只输出语音，文字来自输出转写 | 强制只用语音模态 | 官方文档 |
| 主动音频 | 永久开启，不接受开关参数 | 不传 `proactivity`（传了还会让插件切到 v1alpha 接口） | 官方文档 + 插件源码 |
| 工具调用 | 默认异步，模型可以在拿到结果前先开口 | 显式设为阻塞：工具返回的是模型必须照做的指示（如"暂不推进"） | 官方文档 + 实测 |
| 温度 | 文本生成接口已弃用该参数 | 不发送 | 官方文档 |
| 输入转写 | 支持语言提示 | 会议模式下提示中文普通话 + 英语 | 实测，见 2.3 |
| 说话人分离 | 实时接口不支持 | 转写统一记为"会场" | 官方文档 |

需要 `livekit-plugins-google` 1.8.3 及以上（1.8.0 不认识 3.8）。

## 2. 实测结果

测试方法：本地启动 agent，用脚本以参会人身份加入会议，播放预先合成的语音
（切题、跑题各两段，其中一段夹杂英文术语），记录主持人的反应和各环节耗时。
测试语音的内容用独立的转写模型核对过。

> 这是合成语音、单人依次发言的测试。真实会议有多人抢话、口音和环境噪声，
> 表现会打折扣。上线前需要用真实会议录音重测，见第 5 节。
>
> 2.1 – 2.6 的数字来自最初的一次性测试脚本。2.7 的模拟会议脚本在仓库里
> （`agent/sim/run.py`），可以重复运行。

除特别说明外，数字来自 `gemini-3.8-live`。备选的 `gemini-3.1-flash-live-preview`
跑过同一套流程，结果相近（跑题检出、撤销约 1 秒内停止、半自动只提示不开口）；
它的转写会在每个汉字之间插入空格，系统在使用前会去掉。

### 2.1 跑题判断（Jev）

| 发言内容 | 偏题概率 | 结果 |
|---|---|---|
| 分析 3 号机良率、模温波动 | 0.02 – 0.07 | 不介入 |
| 建议更换温控器、指定负责人（夹杂英文） | 0.02 – 0.03 | 不介入 |
| 聊团建去哪、昨晚的球赛 | 0.99 | 介入 |
| 聊周末看房、首付 | 0.99 | 介入 |
| 讨论下周排产（属于另一个议题） | 0.94 | 介入，原因"跳到了其他议题" |
| 抱怨采购审批慢（擦边） | 0.48 – 0.53 | 不介入（低于阈值 0.85） |

切题与跑题的概率拉得很开，默认阈值 0.85 有足够余量。擦边的内容落在中间，不会触发自动打断。

Jev 官方说明英语是其主要训练语言，中文"能处理但不如英语"。上表的中文样本判断都正确，
但样本很少，不足以代表真实会议。

### 2.2 延迟

从"发言人说完跑题的那句话"到各个节点：

| 环节 | 耗时 | 说明 |
|---|---|---|
| 说完 → 转写文本到达 agent | 2.1 – 3.8 秒 | Gemini Live 按语音停顿分段交付转写，这一段不受我们控制 |
| 转写到达 → Jev 给出判断 | 约 0.4 秒 | 连接保持打开时。连接重建时约 1.8 秒 |
| 判断 → 看板亮起提示 | 几毫秒 | |
| 提示 → 主持人开口 | 约 1.4 秒 | |
| **说完 → 看板提示** | **2.5 – 4.2 秒**（4 次测量：2.5、2.7、2.8、4.2） | |
| **说完 → 主持人开口** | **3.9 – 5.6 秒**（4 次测量：3.9、4.3、5.5、5.6） | |

**对照 PRD 的 3 秒目标**：4 次测量中有 3 次看板提示在 3 秒内出现，1 次超出。
我们自己可控的部分（转写到达之后）只占约 0.4 秒，瓶颈在转写交付。
以上是从"说完"起算；发言人一口气讲十几秒不停顿时，转写要等停顿才到，
从"开始跑题"起算的延迟会长得多（测试中为 11 – 19 秒）。
这一节是改进前的数字。接入流式识别和预制打断语音之后的结果见 2.7。

两处优化是实测后加上的：

- **Jev 连接保活**：HTTP 客户端默认 5 秒空闲就断开连接，会议中发言间隔常常超过 5 秒，
  于是每次判断都要重新握手（1.8 秒）。把保活时间调长后稳定在 0.4 秒。
- **主持人可以在别人说话时开口**：框架默认把主持人的每句话压到全场安静后才播放，
  打断因此变成"等发言人自己停下"（实测晚 9 – 12 秒）。会议模式下已关闭这一限制。

### 2.3 输入转写的语言提示

同一段语音，各转写两次：

| 设置 | "模温波动……模温机的控制器" 的转写 |
|---|---|
| 默认 | 磨损波动……磨损机的控制器（两次都错） |
| 提示中文普通话 + 英语 | 模温波动……模温机的控制器（两次都对） |

转写同时是跑题判断和纪要的输入，因此会议模式下默认带上语言提示。
另外测试了自定义词表，在这段语音上没有带来额外改善。

### 2.4 撤销、半自动、配置变更

| 场景 | 结果 |
|---|---|
| 撤销打断 | 主持人在 0.8 – 1.3 秒内停止发言，该次记为误判，冷却时间加倍 |
| 半自动模式 | 只出现提示，主持人不开口；点击"打断并引导"后约 2 秒开口 |
| 会中切换自动 / 半自动 | 原地生效，会话不重启 |
| 会中修改指令 | 会话重启，主持人不离开房间，议程与决议保留 |

### 2.5 打断用语

打断时说的话由代码给出（`agent/intervention.py` 的 `spoken_interruption`），模型照原话说。
只用日常用词，只报议题名称；议题目标和跑题原因已显示在看板上，不再念出来。

| 主持风格 | 实测时说的话 | 触发方式 | 时长 |
|---|---|---|---|
| 果断控场型 | 各位，先停一下。这个话题我们会后再聊，现在先回到「3 号注塑机良率下降原因分析」。 | Jev | 6.7、6.7、7.5 秒 |
| 果断控场型 | 各位，先停一下。这个话题先放一放，现在先回到「……」。 | 人工 | 6.5、6.7 秒 |
| 温和引导型 | 不好意思，打断一下。这个话题先放一放，现在先回到「……」。 | 模型自行发现 | 6.8、6.9 秒 |
| 极简报时型 | 请先回到「……」。 | Jev、人工 | 3.7、3.9 秒 |

第二句随跑题原因变化：无关闲聊（"这个话题我们会后再聊"）、跳到其他议题（"这件事后面再谈"）、
纠缠细节（"这个细节会后再谈"）、争执（"这一点先不争了……把结论定下来"）。
Live 模型自行发现或人工点击触发时没有原因分类，用通用句（"这个话题先放一放"）。
后三种原因的句子只有单元测试覆盖，没有实际播出过。

改动前由模型按提示词自行组织语言，一次打断约 15 – 17 秒。
以上均在 `gemini-3.8-live` 上测得，每次说出的内容都与给定的原话一致，没有多加内容。
议题名称越长，时长越长。用改动前的提示词（已保存的预设里可能还是旧版）配新 agent 测了 2 次，
说的同样是新话术。

### 2.6 纪要整理

用一场测试会议的转写（10 段）调用，约 11 秒返回。讨论要点与转写一致；
没有讨论到的议题如实留空；已登记的决议没有被重复列为待确认事项。

### 2.7 模拟会议（2026-09-28）

`agent/sim/run.py` 自动开一场约 3 分钟的会：4 位参会人（各用一种合成音色）对着同一支
会议室麦克风发言，中途有一段 17 秒的闲聊，形成一条决议、一条未决事项，最后要求总结。
脚本只负责说话，打断、登记、点名、推进议程、总结都由主持人自己完成。

共跑了 9 轮，每轮发现的问题修复后再跑下一轮。第一轮与最后一轮（`gemini-3.8-live`）对比：

| 项目 | 第一轮 | 最后一轮 |
|---|---|---|
| 开始跑题到看板提示 | 19.8 秒（等发言人把 17 秒说完） | 6.2 秒 |
| 提示到主持人开口 | 1.6 秒 | 0.5 秒 |
| 发言人被打断停下 | 没有被打断，全部说完 | 第 7.7 秒 |
| 议程推进 | 没有推进；之后讨论下一议题被当成跑题打断 | 点名答完后自动推进 1 次 |
| 点名 | 逐个点名，每次约 10 秒，且在对方已经表态之后 | 一句话点完两人 |
| 未决事项 | （第二轮起）同一件事登记了 2 条 | 1 条 |
| 纪要的讨论要点 | 0 条（被程序丢弃） | 8 条 |
| 主持人说话总时长 | 75 秒 | 59 秒 |
| 全程 | 232 秒 | 204 秒 |

"开始跑题到提示"的 6 秒里，大约 4 – 5 秒是发言人说出第一句闲聊所需的时间：
内容还没说出来之前无从判断。连续三轮的结果是 6.0、6.2、6.5 秒。

**修复的问题**

| 问题 | 原因 | 处理 |
|---|---|---|
| 连续讲话时察觉不到跑题 | Live 模型的转写要等发言人停顿才交付 | 跑题判断改用一路流式识别 |
| 接上流式识别后偏题概率只有 0.4 – 0.5 | 判断窗口取最近 20 秒，把上一位的切题发言也算了进去 | 只看当前这段话的最近 8 秒，之前的内容只作背景 |
| 提示发出后主持人仍等对方说完才开口 | Live 模型只在会场停顿时开口；框架里的预制语音也要排队等它 | 打断语音预先合成，走单独的音轨直接播放 |
| "请主持人总结并结束会议"被当成跑题 | 相对当前议题它确实"无关" | 判断标准写明会议流程用语不算跑题；判断结果自相矛盾（偏题但原因是"未偏离"）时不打断 |
| 议程不推进 | 点名一次一人、每次一轮对话，跟不上会议节奏 | 一次点完所有还没表态的人；推进被拒时说明还差谁 |
| 讨论转到下一议题被打断 | 系统仍停在上一议题 | 当前议题已有结论时改为提示推进，不当作跑题 |
| 决议复述、点名用语啰嗦 | 由模型自行组织语言 | 改为代码给出的固定句子 |
| 未决事项重复登记 | 模型听到"定不下来"登记一次，有人提议登记时又登记一次 | 同一议题下内容相近的视为同一条，更新而不新增 |
| 重复推进同一议题 | 模型在宣布之前又收到发言，再调一次 | 第二次调用不再重置议题状态 |
| 纪要讨论要点为空 | 模型抄议题标题时带上了"（计划 1 分钟…）"，与配置对不上 | 标题比较时忽略空格和后缀，对不上时按顺序对应 |
| 纪要里最后一项议题显示"进行中" | 没有"会议结束"的状态 | 已有结论的议题显示"已完成" |
| 看不出模型调用了什么工具 | 没有日志 | 每次工具调用记录参数和返回 |

**备选模型 `gemini-3.1-flash-live-preview`** 跑了 1 轮：打断、决议、点名、推进、总结都完成了，
但在正常讨论时插话 2 次（共 19 秒），未决事项的跟进人记错（记成了王部长）。
主持人说话 89 秒，比参会人还多。

**没有解决的问题**

| 问题 | 情况 |
|---|---|
| Live 会话卡死 | 9 轮里出现 1 次：开场后约 50 秒没有交付任何转写，随后停在"思考中"。原有的自动恢复在 45 秒后重建了会话。新增了一条更快的判断：流式识别已经听到完整的句子、而 Live 模型 20 秒没有任何转写时，直接重建。这条新判断还没有在真实卡死中触发过 |
| 转写里的专业词错误 | "注塑机"听成"住宿机"、"良率"听成"凉率"、"模温机"听成"磨温机"。纪要整理时靠上下文纠正了，看板上的实时转写仍是错的 |
| 短促杂音 | 模型决定不说话时偶尔发出不足 1 秒的声音，每场 0 – 2 次 |
| 点到的人是否都答了 | 系统不区分说话人，只能确认"点到了"，不能确认"每个人都答了" |
| 打断语音的音色 | 由语音合成模型生成，与 Live 模型的声音同名但不完全一样 |

## 3. 已知局限

| 局限 | 影响 | 现状 |
|---|---|---|
| 不区分发言人 | 纪要无法写"谁说了什么"；"已表态"需要人工勾选 | 实时接口不支持。离线方案见第 4 节 |
| 转写按停顿分段到达 | 看板上的实时转写在发言人停顿后才出现 | 跑题判断已改用流式识别，不受影响（2.7 节） |
| 模型选择沉默时偶尔仍有约半秒的声音 | 听感上是一次很短的杂音 | 3.8 Live 的行为；提示词已要求"完全不输出"，转写面板会过滤掉这类空内容 |
| Live 会话偶发卡死 | 测试中出现过一次：连续调用工具后停在"思考中"，不再产生转写 | 已加自动恢复：超过 45 秒自动重建会话，议程与决议保留 |
| 会议记录只存在浏览器本机 | 换电脑或浏览器看不到 | 本次范围之外 |

## 4. 本地部署的候选模型

本次**没有接入**任何本地模型，这一节是为后续决策准备的调研结果。

> 2026-09-28 更新：数据私有化的方向改为优先评估 Cloudflare Workers AI，
> 不再以本机显卡部署为前提，见 [improvement-plan.md](improvement-plan.md)。
> 本节保留作参考。

把实时链路换成本地模型意味着改成"语音识别 → 判断 → 语音合成"的级联结构，
并需要一台带 NVIDIA 显卡（建议 24 GB 显存）的 Linux 或 WSL2 服务器。
它同时能解决上面两个最大的局限：说话人分离和转写延迟。

### 4.1 近 10 天（2026-09-17 至 09-27）发布或更新的模型

发布日期来自 Hugging Face 接口，属"官方文档"级别；性能数字均为模型卡自述，属"未验证"。

| 模型 | 用途 | 许可证 | 要点 | 顾虑 |
|---|---|---|---|---|
| `Edge0/Audio8-ASR-Infinite` | 流式语音识别 | Apache-2.0 | 09-21 发布。中英文，延迟 240 – 560 毫秒，长会议内存占用不增长。约 8.5 GB 显存 | 自称预览版；需要运行仓库自带代码；**是否输出时间戳未说明**，而时间戳是与说话人分离对齐的前提 |
| `nvidia/Nemotron-3-Diarization` | 说话人分离 | OpenMDW-1.1（可商用） | 09-01 发布，09-24 更新。流式，最多 8 人，支持重叠说话，训练数据含中文 | 只支持 NVIDIA 显卡 |
| `XiaomiMiMo/MiMo-V2.6-Distill-Qwen-9B` | 文本模型 | MIT | 09-21 发布 | 模型卡未提及中文效果 |
| `orcarouter/OrcaSAQ-2-27B` | 文本模型 | Apache-2.0 | 09-24 发布。27B 模型压缩到 16 GB 显存可运行 | 需要自定义推理内核 |
| `netease-youdao/Confucius4-R2T2` | 流式语音识别 | 不明 | 09-10 发布 | **许可证条款查不到**，未确认前不要使用 |

### 4.3 建议的推进顺序

1. **先补会后的说话人分离**，不动实时链路：会议结束后把录音交给离线模型
   （如 MOSS-Transcribe-Diarize）重新转写并标注发言人，用于纪要。改动小，收益直接。
   前提是保存会议录音，这涉及 PRD 中的留存与加密要求。
2. **再评估流式识别**：用 5 – 10 场真实会议录音对比 Audio8 与 Qwen3-ASR 的中英混合识别率，
   并确认 Audio8 能否给出时间戳。
3. **最后才是实时链路本地化**，且只在前两步证明效果可接受之后。

不更换实时模型也能缩短延迟的一条路：并行接一路 `gemini-3.5-transcribe-live`，
它能给出识别的中间结果，可以在发言人说话途中就开始判断。代价是多一路实时会话的费用，
以及该接口单次会话 10 分钟的上限需要处理重连。
